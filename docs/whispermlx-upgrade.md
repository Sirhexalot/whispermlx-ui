# WhisperMLX upgrade experiment

Candidate: `whispermlx==3.14.0`, `mlx==0.32.3`, `mlx-metal==0.32.3` (installed app runtime: 3.12.2 / 0.32.0 / 0.32.0). Keep the managed runtime at `~/.local/share/whispermlx-ui/venv` unchanged until end-to-end validation passes. The app resolves this managed environment by default; for a test run set `WHISPERMLX_PYTHON` to a separate environment's interpreter. The initial experiment overlays these three candidate packages on the existing runtime's other dependencies; it is not a fully independent dependency-resolution test.

The app's `bin/whispermlx_runtime.py` replaces `transcribe_task` and wraps `load_model`, `load_align_model`, and `align` at runtime. Compared with 3.12.2, the upstream `transcribe.py` in 3.14.0 additionally passes the optional `interleaved_context` argument to `model.transcribe`; the existing hooks and alignment call sites remain in place. Existing five unit tests pass against the combined candidate, the CLI version command starts, and a basic MLX array operation succeeds. These checks do **not** establish transcription quality or end-to-end compatibility.

Smoke test (2026-10-01): macOS `say -v Anna` generated a roughly 10-second German recording. With the candidate environment, `bin/whispermlx` using `large-v3`, German and Silero produced the expected text. Alignment completed in a separate CPU worker (reported 1370 MiB peak RSS); output JSON contained 23 word segments with timestamps. A second run with identical options reused both the raw transcript and the cached alignment block. This synthetic single-speaker sample does not establish quality on real recordings, long-file memory behavior, or diarization compatibility.

Long-file test (2026-10-01): a **temporary copy** of a private 100-minute recording was processed with `large-v3 --language de --vad_method silero`, without diarization. The source and existing results were not changed or committed. ASR processed 213 VAD chunks; CPU alignment completed all 54 blocks. Output contains 13,487 words with valid start/end timestamps spanning 5,999.8 seconds. Wall time was 3,493 seconds; `/usr/bin/time -l` reported maximum resident set size 2,844,491,776 bytes for the parent and zero swaps, while alignment worker logs reported at most 2,713 MiB per worker. These are separate process measurements, not a combined peak. A second run reused the raw transcript and all 54 alignment blocks in 6.74 seconds. An earlier result for the same recording contains 13,425 words ending at 6,000.4 seconds, but its settings have not been verified as identical, so word counts are **not** an accuracy comparison. Human review of transcription quality and diarization on the entire long file remain open.

Diarization and bundle smoke test (2026-10-01): a temporary five-minute excerpt of that recording was processed with the candidate and the existing **local** pyannote pipeline, without a token or upload. ASR and three CPU alignment blocks completed; 67 output segments were assigned across four speaker labels and the separate `word_segments` list contained 590 timed words (speaker labels are on `segments`, not on the top-level `word_segments`). `./build.sh Debug` succeeded, the signed staged app launched and remained running, and its **bundled** CLI reused raw and alignment caches when directed at the candidate Python environment. This does not test clicking the SwiftUI controls, macOS microphone/screen permissions, recording/mixing, or whether the app picks up an updated managed environment after release. Those checks remain open; do not interpret app launch as a complete UI test.

Before switching the app runtime: test representative German/English recordings with and without diarization, verify word timestamps and outputs, interrupt alignment and resume with the same settings, and compare memory and runtime with 3.12.2. Run in a separate environment and use separate copies of recordings so checkpoints from the baseline are not overwritten. In particular, check whether the new optional context mode improves names/punctuation before exposing it in the UI; it is off by default.
